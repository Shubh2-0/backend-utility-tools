# Optimistic vs pessimistic locking in MySQL

_Generated 2026-05-18_

95% of MySQL users are misusing locking mechanisms in production me, and it's a recipe for disaster. When it comes to concurrent database access, you have two primary options: optimistic and pessimistic locking. I've seen many engineers opt for pessimistic locking by default, but is it really the best choice? 

In pessimistic locking, a lock is acquired on the data before it's even read, which can lead to significant performance bottlenecks scale pe. On the other hand, optimistic locking assumes that multiple transactions can complete without affecting each other, and only checks for conflicts when the transaction is committed.

Here's an example of optimistic locking using MySQL and Java:
```java
@Entity
public class User {
    @Version
    private Long version;
    // other fields
}
```
```sql
UPDATE users SET version = version + 1, ... WHERE id = ? AND version = ?
```
